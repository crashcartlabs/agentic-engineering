Foundations: Spec, Plan, TDD

Product altitude

Spec: what to build

The spec defines the user problem, required behavior, acceptance cases, edge cases, and non-goals. It should be understandable by product, design, engineering, QA, and agents. This repo's first-class skill for that is /spec.

Engineering altitude

Plan: how to build it

The plan translates the spec into architecture, data changes, task order, test seams, validation commands, risks, and rollback. This repo's first-class skill for that is /plan.

Code altitude

TDD: prove each slice

TDD is the inner implementation loop: write the failing behavior test, make it pass with minimal code, then clean up without changing behavior. This repo's first-class skill for that loop is /tdd.

Boundary

/spec writes the product contract, not the build plan

Use /spec to settle users, behavior, acceptance cases, edge cases, and non-goals. Use /plan after that to decide architecture, task order, exact test seams, validation commands, rollout, and rollback.

Day 1 intake

Start with this

Use /wayfinder when the app idea is still foggy

Choose this when you do not yet know the product boundary, first spec, major integrations, data model, or sequence of decisions. The output is a GitHub issue map: destination, decisions so far, unresolved tickets, and out-of-scope boundaries.

Skip ahead when clear

Use /spec, then use /plan

Choose this when the feature can already be phrased as a product requirement with acceptance behavior. The spec defines the "what"; /plan turns it into one buildable implementation contract under plans/.

For a brand-new app, day 1 starts in the app repo, not this repo:

  1. Create or open the app repo/folder.
  2. Run /new-app to add app-specific AGENTS.md, a thin CLAUDE.md adapter, DEVLOG.md, temporary TODO.md, and the spec/plan artifact directories.
  3. Run /wayfinder if the idea still needs mapping; otherwise run /spec for the first product contract and then run /plan for the first concrete slice.
  4. Do not build product code inside agentic-engineering unless the product is dev tooling.

Skill map by build phase

Phase Primary skill Use when Durable output
0. Repo setup /new-app, AGENTS.md, CLAUDE.md A new app repo needs local rules, stack commands, deployment assumptions, and a definition of done. Repo instructions, initial gate, app-specific conventions.
1. Ideation and product spec /spec, /wayfinder, /grilling, /domain-modeling, /research The product intent, acceptance behaviors, edge cases, or user vocabulary are not yet precise. specs/<date>-<topic>.md, optionally backed by wayfinder map/tickets or GitHub issues.
2. Technical planning and architecture /plan, /codebase-design, /prototype-spike The spec is clear enough to translate into files, seams, data changes, dependencies, phases, validation, and rollback. plans/<date>-<topic>.md with status, phases, success criteria, test seams, and validation commands.
3. Developer inner loop /execute, executor, /tdd, /sandbox The plan is approved and implementation should proceed in isolated, test-first vertical slices. plan/<slug> branch, phase commits, red -> green evidence, updated plan status/notes.
4. CI verification gates /review-plan, /code-audit, /security-audit, /commit The branch must prove it satisfies the plan/spec before it can be merged. /review-plan + /code-audit run on every change by default; /security-audit is risk-gated. Tracked review/audit reports, green local gate, coherent commits.
5. CD and live release /ship, /babysitting-pr The verified branch is ready for a PR, CI, human review, merge, and the app repo's deployment pipeline. Evidence-bearing PR, merge-ready state, deploy evidence from the app's own CD system.
6. Day-2 operations /bugfix, /diagnosing-bugs, /todo-cleanup, /cleanup-worktrees, /handoff The feature is live or merged and needs monitoring follow-up, incident work, backlog conversion, or workspace cleanup. Incident notes, follow-up issues, cleaned worktrees, durable session handoff when needed.

Side tools and when they enter

Risk isolation

Use /sandbox before unfamiliar installers, destructive git experiments, untrusted code, hook setup experiments, mutation-heavy dogfooding, or a TDD/deployment experiment that should not touch the live machine.

Parallel work

Use /cmux when the work can fan out into independent agents or worktrees. Use the cmux guide for fleet mechanics.

Architecture review

Use /improve-codebase-architecture for periodic or heavyweight architecture scans, not for every feature.

Bug diagnosis

Use /diagnosing-bugs when the cause is unknown, including day-2 incidents. It proves the cause before the TDD regression loop starts.

Deployment policy

This repo does not yet have a dedicated CD or SRE-agent skill. The app repo's own deployment pipeline owns canaries, blue-green releases, feature flags, smoke tests, observability, and rollback policy.

Skill changes

Use /build-skill, /dogfood, and /skill-safety-scan when changing agent behavior rather than app code.

Session transfer

Use /handoff when hot conversation context must survive a fresh session. It does not replace the plan file.

Tracking state between sessions

Question Source of truth
What is the product contract? The spec artifact under specs/: PRD, feature brief, Gherkin-style acceptance cases, or wayfinder-derived product decision.
Where are we in the build? The active plan file under plans/: status, checkboxes, amendments, execution notes.
Where did the last session stop? /handoff only when the stop point depends on hot conversation context.
What has happened over time? DEVLOG.md, newest first.
What work is deferred? GitHub issues; TODO.md is only temporary scratch.
What is the broad app roadmap? The /wayfinder map issue and its child tickets.
What PR is still being watched? The PR state plus the babysitting-active label.
What is live? The app repo's release/deployment evidence: tags, environment dashboard, rollout notes, feature-flag state, and incident records.

Operating checklist

  1. Create the app repo first. Run /new-app there. Do not start product code inside agentic-engineering and move it later.
  2. Choose the first routing gate. If the idea is foggy, run /wayfinder; if the product behavior is clear, run /spec.
  3. Do not skip the spec. Capture what the software must do, who it is for, acceptance behavior, edge cases, non-goals, and any executable acceptance tests.
  4. Make the plan executable. Turn the spec into testable success criteria, named seams, validation commands, risks, rollout notes, and rollback strategy.
  5. Execute only approved plans. /execute owns the branch and phase commits; /tdd owns strict red -> green slices where the plan requires them.
  6. Review before shipping. Run /review-plan first, then deeper audits when risk warrants them.
  7. Ship with evidence. /commit runs the repo gate before commits; /ship opens the PR with verification evidence; the app's CD pipeline owns live rollout.
  8. Operate and clean up. Use /babysitting-pr for live PR follow-through, /diagnosing-bugs for incidents, then /cleanup-worktrees and /todo-cleanup after merge.
